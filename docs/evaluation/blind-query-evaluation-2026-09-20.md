# Blind Query Generation Evaluation — 2026-09-20

This note records a small, auditable evaluation of **owner/task language → code-retrieval query generation** before adding semantic retrieval, embeddings, or a vector database to PACT.

It advances the evaluation question in #123. It is directional evidence, not a benchmark claiming model-independent retrieval quality.

## Question

PACT already has deterministic lexical / symbol / import-neighbor retrieval. The open question was whether poor owner-language recall requires a heavier semantic retrieval subsystem, or whether an Agent can usually bridge the vocabulary gap by generating a small set of code-oriented search hypotheses.

The evaluation therefore separates:

- **direct task retrieval** — the task wording alone;
- **blind Agent query generation** — queries frozen before the historical target diff/oracle is inspected;
- **structure-aware blind generation** — the Agent may inspect bounded pre-change repository structure/vocabulary before freezing queries;
- **post-oracle diagnostic** — explicitly hindsight-only; useful for diagnosing engine capability, never counted as blind evidence.

All compared Context arms use the same configured medium-risk budget unless noted:

- code limit: 12;
- materialization token budget: 40,000 estimated tokens.

Low recall is data, not a CI failure.

## Query-generation provenance

Queries in the valid blind cases were generated by ChatGPT GPT-5.6 Sol during the same PACT review session.

Before each oracle reveal, the task/ref/query set was posted to GitHub issue #123. Temporary GitHub Actions workflows then reproduced Context generation from pinned pre-change commits. Those temporary PRs were closed without merging.

The query-generation step did not measure wall-clock Agent overhead, owner comprehension, or human interaction cost.

## Case 1 — inaccessible target; no retrieval result

Repository: `ningcol/xiaohongshu-auto-publish`

Target commit: `668e796ce7344b154e0877f9b8b891fb6e76444b`

Frozen task:

`更新MCP处理器主文件：集成互动功能处理器、添加互动功能路由、完善错误处理机制`

Frozen blind queries:

1. `MCP handler interaction`
2. `interaction handler routes`
3. `MCP error handling`

The GitHub-hosted runner could not anonymously clone the target repository. No PACT Context ran and no recall result was produced.

This is a **target-access / harness failure**, not a retrieval failure. Private credentials were not added to PACT CI merely to obtain an evaluation result.

## Case 3 — task-only blind generation, three-file oracle

Repository: `ningcol/DouBaoFreeImageGen`

Base: `f4edad8ea7b49a2f0e92da2aac599350ed042c32`

Historical target: `9ca173e37341e4e1a80cadc427737510a3a1eaa5`

Task described debugger/EventStream image URL acquisition plus Cookie clearing/settings.

Source oracle:

- `DoubaoMcpBrowserProxy/background.js`
- `DoubaoMcpBrowserProxy/content.js`
- `DoubaoMcpBrowserProxy/options.js`

Blind queries frozen before oracle:

1. `debugger EventStream image URL`
2. `clear cookies settings`
3. `image extraction debugger`

| Metric | Direct task | Blind Agent |
|---|---:|---:|
| Oracle recall | 0/3 = 0.0 | 2/3 = 0.667 |
| Selected code files | 0 | 3 |
| Selected estimated tokens | 0 | 7,185 |
| Dropped candidates | 0 | 0 |
| Known unknowns | 3 | 1 |

Blind retrieval found `background.js` and `content.js` but missed `options.js`.

### Hindsight diagnostic

After the oracle was revealed, one explicit project-vocabulary query was added:

`options settings storage`

This diagnostic is **not blind evidence**.

It changed the selected Context from 3 files / 7,185 estimated tokens to 4 files / 7,401 estimated tokens and reached 3/3 oracle recall with zero dropped candidates.

The pre-change `options.js` already contained settings/storage concepts such as `saveOptions`, `loadOptions`, and Chrome storage. This supports a narrower diagnosis:

> the existing retrieval stack could find the integration point when supplied the project's own vocabulary; the blind task-only Agent failed to generate that vocabulary.

That finding argues for testing better project-aware query generation before adding a new semantic retrieval subsystem.

## Case 4 — structure-aware blind generation, five-file oracle

Repository: `ningcol/ziliu`

Base: `7542c755ebb0987aeb1415dba2c9f7a71b173993`

Historical target: `a900bd01d8dcb1098adb151a0eff2a32e908c58b`

A first temporary workflow exposed only bounded pre-change repository structure. It contained no target commit and computed no oracle.

Pre-change structure included project vocabulary such as:

- `src/app/api/parse-feishu/route.ts`
- `parseFeishuContent`
- `processImagesInHtml`
- `uploadImageFromUrl`
- `src/components/editor/feishu-import-dialog.tsx`
- `src/lib/services/image-service.ts`
- `src/lib/services/imageUploadService.ts`

Based only on the frozen task summary and that pre-change structure, the following queries were frozen:

1. `parseFeishuContent processImagesInHtml uploadImageFromUrl`
2. `feishu-import-dialog loading progress toast`
3. `image-service uploadImageFromUrl retry timeout`

Only after those queries were recorded was the historical target diff revealed.

Source oracle:

- `src/app/api/parse-feishu/route.ts`
- `src/components/editor/editor-layout.tsx`
- `src/components/editor/feishu-import-dialog.tsx`
- `src/components/editor/simple-editor.tsx`
- `src/lib/services/image-service.ts`

### Important limitation

The frozen English task summary omitted two details present in the original historical commit message, including removal of `simple-editor` and the Vercel-timeout change. The task summary was **not corrected after oracle reveal**.

Therefore a miss on `simple-editor.tsx` must not be interpreted as pure retrieval failure.

### Initial comparison

| Metric | Direct frozen task | Structure-aware queries only |
|---|---:|---:|
| Oracle recall | 4/5 = 0.8 | 3/5 = 0.6 |
| Selected code files | 12 | 8 |
| Selected estimated tokens | 36,518 | 39,892 |
| Candidate estimated tokens | 99,881 | 79,226 |
| Dropped candidates | 24 | 13 |
| Dropped for token budget | 1 | 13 |
| Dropped for count limit | 23 | 0 |

The structure-aware query set found `editor-layout.tsx`, which direct retrieval missed, but lost `feishu-import-dialog.tsx` and `simple-editor.tsx`.

This was evidence that **more project-specific queries are not automatically better**: query specificity can concentrate the Context on large service files and consume the token budget before UI integration points are materialized.

## Product-composition diagnostic and #130

PACT #119 had already established a product rule: high-level `task prepare` keeps the original task wording first and appends Agent `--query` values as supplemental hypotheses.

The initial Case 4 low-level comparison had evaluated direct and structure-only query sets separately, so a third diagnostic combined only already-frozen inputs:

1. the frozen task wording;
2. the three frozen structure-aware queries.

No new oracle-derived vocabulary was added. The decision to run this fusion arm was post-result, so it is a product-behavior diagnostic rather than a pre-registered blind arm.

### Before #130

Current symmetric query fusion produced:

- oracle recall: 2/5 = 0.4;
- selected code files: 8;
- selected estimated tokens: 39,966;
- dropped candidates: 28, all because of token budget.

Adding supplemental queries had therefore made the recommended task Context **worse than direct retrieval**.

### Rejected fix

A first prototype increased the generic RRF weight of the primary query.

It was rejected because:

- the pinned ziliu reproduction stayed at 2/5 = 0.4;
- the existing four-case historical benchmark's curated multi-query weighted recall regressed from 0.667 to 0.556.

This was useful negative evidence: generic RRF tuning was not the right layer.

### Final #130 behavior

#130 leaves peer `discover` fusion unchanged.

Only when Context receives the original task wording first plus supplemental queries does it:

1. resolve the direct task-only Context under the normal count/token budgets;
2. preserve those already-selected files as canonical;
3. append fused supplemental/wider candidates as fallback for remaining capacity.

The pinned ziliu reproduction then produced:

- direct: 4/5 = 0.8, 12 files, 36,518 estimated tokens;
- task + supplemental queries: 4/5 = 0.8, the same 12 files and same estimated-token usage.

The existing four-case curated peer multi-query benchmark simultaneously retained its prior weighted recall of 0.667.

This establishes a useful safety property:

> adding Agent search hypotheses to the recommended high-level task path does not silently evict the Context already selected for the owner's task under the same budgets.

It does **not** claim that supplemental queries will improve a task whose direct Context has already filled its hard count/token capacity.

## What the evidence currently supports

Across the valid blind cases:

- direct owner/task wording can have a severe vocabulary gap;
- small Agent-generated query sets can materially improve recall;
- task-only Agent generation may still miss project-specific integration vocabulary;
- bounded pre-change project structure provides useful vocabulary, but structure-aware queries are not automatically superior;
- token/count selection and query-composition policy materially affect final Context quality;
- the lexical/symbol/graph stack can retrieve some missed integration points when supplied the right project vocabulary;
- generic multi-query fusion and task-primary supplemental search are different use cases and should not be forced into one ranking policy.

## Current decision

Do **not** add embeddings or a vector database based on this evidence.

The next lower-cost path is:

1. keep owner/task wording authoritative in the recommended high-level task path;
2. let Agent queries supplement rather than silently replace task-selected Context;
3. generate queries from bounded pre-change repository structure, vocabulary, and remembered-feature inspection when needed;
4. retain equal-query low-level fusion for deliberate exploratory retrieval;
5. continue collecting blind cases across projects/languages before escalating retrieval architecture.

Semantic retrieval should be reconsidered only if additional blind, project-aware query generation still fails on relevant integration points **even when the pre-change repository exposes usable vocabulary**, or if the lexical candidate space becomes too broad for deterministic budgets at realistic project scale.

## Remaining unknowns

This evaluation does not measure:

- owner comprehension;
- owner interruption/clarification count;
- wall-clock query-generation overhead;
- model-to-model variance;
- retrieval quality on private repositories unavailable to reproducible CI;
- whether extra Context files outside the historical diff are semantically useful;
- long-term behavior on very large monorepos;
- a single PACT quality score.

Do not collapse these results into one score.
